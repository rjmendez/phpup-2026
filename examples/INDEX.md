# Sample index

2026-10-21: four samples (two pcaps, two http dumps, two logs, two eve.json
entries) built around the retired single-request spray/byte-offset theory
were removed, not kept as "historical" -- they validated rule IDs
(9109628-9109632, sigma 7d9e1b23, YARA phpup2026_spray) that no longer
exist. See `ANALYSIS.md` for why. Two real captures from that era survive
below because they are still correct under the current understanding: the
benign control (still the false-positive check for the surviving rules)
and the stall-no-crash capture (which is *why* the old theory was
corrected in the first place -- good evidence, not bad data).

2026-10-21, later the same day: a fifth pcap was added specifically to
check an open question raised during an unrelated Azure-Sentinel PR
review (Azure/Azure-Sentinel#15377) -- whether `rules/suricata.rules`'
duplicate-header-name signal (9109633) could cross a MIME part boundary
and false-positive on an ordinary legitimate multi-file upload, the way
a KQL version of the same idea turned out to. Built a real, genuinely
benign 4-file upload (each file 3 bytes of real content, not empty) to
test it directly. Result: 9109633 did NOT fire -- confirmed safe, not
just asserted. A *different* rule, 9109635 (empty file fields), DID
fire on this same legitimate traffic -- a real, reproducible false
positive, now retired in `rules/suricata.rules` with this evidence.
